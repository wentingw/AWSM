## 1. 文章要回答什么

建议英文标题：**From Video to Executable Worlds: Building Semantic 3D Scenes with GPT‑6 Astra**。

中文工作标题：**从视频到可执行世界：用 GPT‑6 Astra 构建有语义、有尺度、可交互的三维场景**。

核心论点是：将几何估计作为测量依据，将 Astra 的视觉理解和工具编程用于构造对象化的场景程序，输出可以编辑、查询、渲染并进入仿真的世界。我们将分别验证外观、几何、语义和执行能力，并测量增加几何约束后发生了什么变化。

需要回答四个问题：

1. 只看图片，Astra 能恢复哪些结构，又会猜错哪些尺寸和不可见部分？
2. 输入估计的位姿与深度，是否改善几何、尺度和跨视角一致性？
3. 用 GT 位姿替换估计位姿后，误差还能降低多少？哪些问题仍来自深度与建模？
4. 对象语义和可碰撞几何，是否让图像目标导航与语言找物真正可执行？

“颠覆 3D 建模、SLAM、空间智能”放在讨论中，以证据说明可能改变的工作方式。现阶段管线仍依赖定位与深度估计，不能宣称已替代 SLAM。语义建图、场景图、程序化重建已有研究先例；我们的贡献必须由这套系统的具体能力和实验说明。

[官方 Astra 模型页](https://developers.openai.com/api/docs/models/gpt-6-astra) 已实际读取并存档，支持公开模型命名和工具编程能力的背景说明，不支持“行业已经被颠覆”的结论。运行时模型 ID、提供方、版本/日期另记录，不能仅凭模型别名推定完全复现。

## 2. 继承结果：哪些可复用，哪些必须补跑

统一使用 **World Lobby 稳定相机轨迹**：录制约 360 秒，8,999 张 RGB，1280×960，25 Hz；同步 IMU 250 Hz；原始采样索引 `0,50,…,8950` 共 180 帧。视频时长、首末时间戳跨度分别保存，不能混为一个时长。

| 实验 | 已有证据 | 本轮处理 |
|---|---|---|
| M1：RGB → Astra/Blender | 纯 RGB 模型已冻结；模型本身没有估计的逐帧相机 | 复用为历史模型；补统一配准与渲染。若做预算控制对照，另建新 run |
| M2：ViPE → Astra/Blender | 原生 ViPE 的 180 帧 pose/depth 已有；现有模型复用了其他管线几何 | 主实验补跑全视频 ViPE，重新生成只依赖 ViPE 几何的模型；180 帧版本留作稀疏输入对照 |
| M3：OpenVINS → MapAnything → Astra | 原 OpenVINS 全程发散；31-clone 修正版仅验证前 62 秒 | 先验证完整序列，再生成对应 depth/model；如仍失败，如实报告 |
| M4：GT pose → MapAnything → Astra | GT 和必要数据已存在，未发现完整实验 | 新跑深度与建模，独立标注 GT-pose 条件 |
| M3b：SfM＋IMU → MapAnything → Astra | 现有成功 Blender 模型实际来自此路线 | 保留为补充对照，不能换名为 M3 |
| M3c：联合离线 VIO → MapAnything → Astra | 已有较新位姿，后续仅做输入同步 dry-run | 位姿作为补充；若要比较完整模型，须补跑 depth/model |

现有记录还给 M1 冻结模型追加了 **RGB-only COLMAP** 相机求解。这是独立的后处理轨迹，不是 Astra 自己估计的相机，更不能据此倒推旧模型使用了这些位姿。

旧 M3b 报告：位姿 ATE 约 0.366 m；可见表面双向平均误差约 0.334 m；GT 可见表面在 10 cm 内的覆盖率约 39.94%。这些数值说明流程已经可运行，也说明“与真实几何精确对齐”尚不能作为既成事实。新的联合 VIO 位姿 ATE 约 0.342 m，尚无相应新模型。这些历史指标口径不同，本轮主表需统一重算。

Office-cafe / IMG_0755 可放附录作为真实视频案例；不与 World Lobby 混入同一 GT 定量比较。

## 3. 四种方法与两个基线

用户列出的项目实际为 **6 个主系统**，全部保留；ViPE、MapAnything 称“几何重建基线”，不笼统称为传统算法。

| ID | 建模可读取的输入 | 流程 | 实验目的 |
|---|---|---|---|
| M1 | 采样 RGB；共同允许的相机标定需明确 | Astra → Blender | 纯视觉构造能力 |
| M2 | RGB + ViPE pose/depth | ViPE → Astra → Blender | 学习几何先验的帮助 |
| M3 | 视频 + IMU + 标定 | OpenVINS metric pose → MapAnything metric depth → Astra → Blender | 传感器约束的场景构建 |
| M4 | 视频 + GT camera pose + 标定 | MapAnything metric depth → Astra → Blender | 位姿质量的诊断参考条件 |
| B1 | 与 M2 相同的 ViPE 输入 | ViPE → 点云/统一表面融合 | 不经过 Astra 的几何基线 |
| B2 | RGB + 共同内参约定 | MapAnything image-only pose/depth → 统一融合 | 通用几何网络基线 |

增设 **B2p**：与 M3 完全相同的 OpenVINS 位姿条件和 MapAnything 深度，直接融合、不经过 Astra。它与 M3 的对照最能说明场景程序生成的收益或损失。M3b/M3c 为额外诊断，不挤掉主方法。

主实验 M2/B1 从完整视频估计逐帧位姿与深度；M3 在完整视频和 IMU 上估计轨迹，M4 读取对应 GT camera pose。建模器统一取 180 个采样视角。MapAnything 可按已验证的滑窗在这些视角推理，但必须记录窗口、重叠、全局坐标锚定与尺度一致性；不能对每窗用 GT 独立调尺度。对外声称“每帧 pose”时，逐帧记录直接估计、插值、IMU 传播或缺失，初始化前不得伪造估计覆盖。

主方法信息预算不同，这是受控增加传感器/几何信息的实验，不是同输入算法排行榜。另设“同几何、是否经过 Astra”的 B1↔M2、B2p↔M3 配对实验，才能讨论语义构造的独立作用。

四种建模统一输出：`scene.blend`、`scene.glb`、构建源码、对象清单与证据帧、材质、碰撞几何；具备关节证据时才输出关节与限制。物体未观察部分、推测尺寸和物理先验必须有来源标记。

共同建模环：**图像理解 → 对象清单 → 几何约束/尺寸测量 → Blender 程序 → 多视角渲染 → 独立验证 → 修订 → 冻结**。建模和独立验证使用 Astra；辅助处理可并行。验证器只能访问该方法允许的输入，不能把 GT 反馈给建模器。M4 唯一额外获准输入是 GT camera pose，不开放 GT mesh、depth 或物体表。

新建模会话使用干净上下文和独立输入包，不继承本次包含 GT 评测信息的分析上下文，不读其他方法的模型或构建源码。可复用通用工具，但不得把旧模型尺寸藏在脚本默认值中；逐方法记录实际输入与文件访问。

### 主表：一种系统一行，四组误差

| 指标组 | 主指标 | 关键口径 |
|---|---|---|
| 位姿 | 平移 ATE RMSE、旋转 RMSE、RPE@1s/10s、有效覆盖 | metric 方法只做统一 SE(3) 坐标规范对齐；Sim(3) 另列，不能掩盖尺度误差 |

## 5. 语义与物理主张如何获得证据

语义：由独立标注记录物体类别、实例、空间关系，统计实例 precision/recall、漏建/多建、语言目标 grounding 正确率。模型自报“这是椅子”不是验证。

几何：验证真实尺度、对象尺寸、支撑面、可通行间隙与局部几何，报告置信/未知区域。最近表面距离之外增加对象对应评估，避免错误物体碰巧靠近而得高分。

物理：分别检查碰撞体完整性、初始穿透、支撑稳定、机器人净空与可执行轨迹。质量、摩擦、惯量、隐藏关节等常常无法从静态 RGB 确定；使用工程先验时应标注“仿真设定”，不能称为测得的真实物性。当前证据目标是几何和碰撞可用性，动态系统辨识另属未来工作。

## 6. 两个下游任务

**无人机：给参考图，找到场景并复拍。** 参考图只保留 RGB；检索重建世界中的候选视点，匹配定位，规划碰撞安全航路，执行并通过图像反馈微调。建议 20 个目标图 × 3 个起点，预先固定；报告成功率、最终位置/角度误差、图像相似度、碰撞和时间。目标 GT pose 只供评价器，不能写进规划器。需要相机俯仰时明确固定相机与机体姿态、或云台的模型，不做瞬移复拍。

**G1：给语言，找到对应物体。** 解析类别/属性/关系，在对象场景图检索候选，用可通行空间规划，调用已验证的 G1 行走控制器，停在可见且满足指令的距离。建议 30 条指令 × 3 个起点，含同类多实例和关系指令；报告 grounding、到达率、SPL、碰撞、跌倒和时间。只做找物，不扩展为抓取。当前未找到 G1 现成资产/控制实验，需独立引入并验证；如果仅做运动学移动，必须明确展示级别，不能称为动态行走成功。

每个任务都分两层：

1. 在 **M3 重建世界** 中感知、规划和执行，验证场景表示本身可用。
2. 保持重建地图，将控制策略放入 **GT 仿真碰撞世界**，测试误差会不会造成撞墙、错认目标或复拍失败。

第二层决定几何真实性是否足以支撑任务；模型内自洽不能单独证明。GT 仿真提供合法的 RGB 等传感观测，但 planner 不读取 GT 地图/目标答案；如为隔离建图问题给各方法提供相同的自定位真值，显式标注 state-oracle 条件。该实验范围为仿真，不包含实机部署。

首轮每方法 1 个完整 run 做工程验证；主结论若比较 Astra 稳定性，使用至少 3 个独立 run，并记录版本、提示、预算、重试与失败，不能只取最优。旧 run 可以放历史复现栏；不把不同预算、不同验证次数的旧结果视作严格受控对照。

先完成 World Lobby 全部用户指定实验。若要声称跨场景推广，推荐再增加至少两个布局/材质明显不同且有 GT 的场景；三场景也只是初步证据，不代表行业规模验证。单场景只报告该场景上的条件结论，不生成虚假的 scene-bootstrap 置信区间。

不预设“必须达到漂亮分数才能发布”的门槛。冻结的是输入协议、统计口径和任务成功定义；高误差、发散、失败都属于结果。OpenVINS 若仍失败，保留 M3 失败状态，并以 M3b 的可运行演示作为明确命名的补充，不能悄悄替换用户定义。

首个完整小规模试验后，再依据实测 GPU 时间与 Astra 用量给出剩余时间/费用范围。历史单次 Astra 建模约一小时只可作为规划参考，不能直接乘法承诺全部耗时或账单。

## 8. 文章结构与视觉设计

建议英文主文约 2,500–3,500 词，中文同步；详细配置、表格与推导放附录。首屏以真实实验短片展示 RGB → 对象场景 → 机器人任务，并提供输入/模型切换。

叙事顺序：**一个直观场景 → 为什么需要可执行表示 → 四条方法与共同建模环 → 5×4 对照 → 四组误差 → 两个下游任务 → 失败与边界 → 对 3D 工具、空间智能和 SLAM 的可能影响 → 可复现资源**。

计划图件：F1 方法流程；F2 5×4 主图；F3 轨迹与时间误差；F4 深度/几何热图；F5 对象语义、尺寸和碰撞；F6 无人机任务；F7 G1 任务；补充 M4 与完整逐帧结果。用真实渲染和测量结果制作图，不用生成图片替代实验图。

相关工作按“几何恢复、视觉质量、语义地图、场景程序、仿真执行”比较。优先核验 ViPE、MapAnything、OpenVINS、3DGS、Hydra、ConceptFusion/VLMaps、SceneScript/Real2Code 以及 Kitchen-Twin/LiteReality，分别说明任务差异，不用未核验的首创表述。
